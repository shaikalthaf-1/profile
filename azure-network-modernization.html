1. Executive Summary

This case study documents the architectural overhaul of Uniper's global cloud network infrastructure in Microsoft Azure. Prior to modernization, Uniper relied on fragmented hub-and-spoke VNet peerings across multiple Azure regions. This legacy topology suffered from uninspected East-West traffic flows, complex manual VNet peering management, inconsistent Network Security Group (NSG) rules, and high administrative overhead when making firewall policy changes.

To eliminate these critical vulnerabilities and support enterprise expansion, I designed and executed a multi-region Azure Virtual WAN (vWAN) and Virtual Hub (vHUB) network architecture integrated with Palo Alto Cloud NGFW inspection clusters and Silver Peak SD-WAN branch connectivity. The entire infrastructure was provisioned using modular, version-controlled Terraform (HCL) code pipelines.

Key Project Achievements:
  • 100% Perimeter Security: Forced 100% of inbound, outbound, and inter-spoke VNet traffic through Palo Alto Cloud NGFW zero-trust inspection nodes.
  • ~40% Faster Provisioning: Created reusable Terraform modules enabling new spoke environment deployments in under 15 minutes.
  • Sub-10ms Latency: Optimized routing paths using Azure Virtual Hub global peering across Primary East US and Secondary West Europe regions.
  • Zero Downtime Cutover: Executed live subscription network migration without disrupting production energy trading services.

2. Business Background

Uniper is a leading international energy company operating critical energy infrastructure, power generation plants, and gas commodities trading platforms across Europe and international markets. The digital transformation of Uniper's operations required migrating legacy on-premise workloads to Microsoft Azure while building modern cloud-native applications on Azure Kubernetes Service (AKS).

As the cloud footprint grew to encompass over 50 subscriptions, multiple business units (Trading, Generation, Corporate IT, Data Analytics) established independent VNet subnets. The rapid growth created an imperative for a centralized, highly resilient, and zero-trust cloud network architecture capable of meeting strict financial regulatory mandates (SOC2 Type II, ISO27001, and NIS2 Directive compliance).

3. Problem Statement & Pain Points

The pre-existing Azure network topology was characterized by significant operational and security deficiencies:

1. Uninspected East-West Traffic & Security Blind Spots

VNet peerings were configured directly between spoke subscriptions without passing through a central firewall. Traffic between trading databases and internal web microservices was uninspected, exposing internal networks to lateral movement risks in the event of a compromised spoke container.

2. High Operational Overhead & Manual Firewall Updates

Palo Alto Virtual Appliances (VM-Series) deployed in legacy DMZs required manual route table entries (UDRs) and manual IPsec tunnel management. Change requests for firewall policy updates required manual ticket approvals that took up to 5 business days to execute via legacy procedures.

3. VNet Peering Scalability Limits

Direct mesh VNet peering scaled exponentially with every new subscription ($N \times (N-1) / 2$), approaching Azure VNet peering limits and creating a maintenance nightmare for cloud operations teams.

4. Inconsistent Public Perimeter Protection

Public web applications lacked a standardized Web Application Firewall (WAF) posture, leading to inconsistent TLS certificate rotation and vulnerable HTTP endpoint exposure.

4. Business Requirements

The enterprise infrastructure committee mandated six strict technical and architectural requirements for the network modernization initiative:

R1: Zero-Trust Perimeter

Force 100% of all inbound, outbound, and inter-spoke VNet traffic through Palo Alto Cloud NGFW inspection nodes without exception.

R2: Automated IaC Provisioning

100% of network resources, route tables, subnets, and Palo Alto firewall rules must be codified using modular Terraform (HCL).

R3: Sub-10ms Cross-Region Latency

Optimize global routing paths between Azure East US and West Europe Virtual Hubs to maintain sub-10ms inter-spoke latency.

R4: Centralized Policy Management

Integrate Palo Alto Panorama API to automate security rule updates during CI/CD execution, cutting change lead time from 5 days to 15 minutes.

5. Solution Architecture & High-Level Design (HLD)

To meet the business requirements, I architected a multi-region Azure Virtual WAN (vWAN) framework. Azure Virtual WAN serves as the enterprise routing backplane, connecting all spoke VNets, on-premise data centers, branch offices via Silver Peak SD-WAN, and remote user VPNs into centralized Virtual Hubs.

Core Architectural Components:

  • Global Azure Virtual WAN Resource: Acts as the top-level management container for global routing across Azure regions.
  • Dual Virtual Hubs (vHUB): Primary vHUB deployed in East US (`10.100.0.0/16`) and Secondary vHUB deployed in West Europe (`10.200.0.0/16`), connected via Azure Global VNet Peering.
  • Palo Alto Cloud NGFW Integration: Deployed directly inside the Virtual Hubs as Managed Network Virtual Appliances (NVAs) with auto-scaling instances.
  • Azure Application Gateway WAF v2: Provisioned in a dedicated DMZ VNet at the perimeter, enforcing OWASP 3.2 rules and SSL termination before forwarding traffic to internal vHUB routers.
  • Custom Virtual Hub Route Tables: Custom routing tables configured to rewrite next-hop paths for `0.0.0.0/0` (Internet) and `10.0.0.0/8` (Internal Spoke) traffic to the Palo Alto NGFW NVA cluster.

8. Terraform & HCL Code Implementation

The entire network infrastructure was written using modular Terraform (HCL). Below are production-grade excerpts of the Terraform modules deployed to Azure:

Module 1: Azure Virtual WAN & Virtual Hub (vHUB) Core (`vhub.tf`)

# Azure Virtual WAN Global Resource
resource "azurerm_virtual_wan" "vwan_global" {
  name                = "vwan-uniper-global-prod"
  resource_group_name = azurerm_resource_group.rg_network.name
  location            = "eastus"
  type                = "Standard"

  tags = {
    Environment = "Production"
    Owner       = "Althaf Shaik"
    ManagedBy   = "Terraform"
  }
}

# Primary Virtual Hub in East US
resource "azurerm_virtual_hub" "vhub_primary" {
  name                = "vhub-prod-eastus"
  resource_group_name = azurerm_resource_group.rg_network.name
  location            = "eastus"
  virtual_wan_id      = azurerm_virtual_wan.vwan_global.id
  address_prefix      = "10.100.0.0/16"
  sku                 = "Standard"
}

# Palo Alto Cloud NGFW Integration inside vHUB
resource "azurerm_palo_alto_next_generation_firewall_virtual_hub_local_rulestack" "palo_ngfw" {
  name                = "ngfw-vhub-eastus"
  resource_group_name = azurerm_resource_group.rg_network.name
  virtual_hub_id      = azurerm_virtual_hub.vhub_primary.id
  rulestack_id        = var.panorama_rulestack_id

  destination_nats {
    name                 = "dnat-appgateway"
    protocol             = "TCP"
    public_ip_address_id = azurerm_public_ip.pip_fw.id
    destination_port     = 443
  }
}

Module 2: Custom vHUB Route Table forcing Palo Alto NGFW Inspection (`routing.tf`)

# Custom vHUB Route Table forcing Zero-Trust Next-Hop
resource "azurerm_virtual_hub_route_table" "vhub_inspection_routes" {
  name                = "rt-vhub-inspection-eastus"
  virtual_hub_id      = azurerm_virtual_hub.vhub_primary.id
  labels              = ["default", "inspection"]

  # Internet-bound traffic route -> Palo Alto NVA Next-Hop
  route {
    name              = "All-Internet-To-Firewall"
    destinations_type = "CIDR"
    destinations      = ["0.0.0.0/0"]
    next_hop_type     = "ResourceId"
    next_hop          = azurerm_palo_alto_next_generation_firewall_virtual_hub_local_rulestack.palo_ngfw.id
  }

  # East-West Inter-Spoke route -> Palo Alto NVA Next-Hop
  route {
    name              = "Inter-Spoke-To-Firewall"
    destinations_type = "CIDR"
    destinations      = ["10.0.0.0/8"]
    next_hop_type     = "ResourceId"
    next_hop          = azurerm_palo_alto_next_generation_firewall_virtual_hub_local_rulestack.palo_ngfw.id
  }
}

9. Deployment & Staged Cutover Process

To avoid disrupting active energy trading applications, the network cutover was executed across four staged phases over a 6-month timeline:

  1. Phase 1: Green-field Infrastructure Provisioning (Months 1–2): Provisioned the Azure Virtual WAN, Virtual Hubs, Palo Alto Cloud NGFW clusters, and Application Gateway WAF v2 in new, isolated resource groups using Terraform pipelines.
  2. Phase 2: Parallel VNet Peering & Validation (Months 3–4): Established secondary vHUB connections to non-production spoke VNets. Validated packet forwarding, Palo Alto rule logging, and sub-10ms latency.
  3. Phase 3: Production Live Cutover (Month 5): Executed a scheduled weekend maintenance window. Swapped default spoke UDR routes to point to the new Virtual Hub inspection table. Achieved zero unplanned downtime during cutover.
  4. Phase 4: Legacy Decommissioning (Month 6): Deprecated legacy hub VNets, un-peered old virtual appliances, and reclaimed unused Azure IP space.

10. Validation, Testing & Auditing

Following cutover, rigorous validation tests were performed to verify performance, security, and resiliency:

  • Throughput & Latency Testing: Ran automated iPerf3 network load tests across spoke VNets. Confirmed 9.8 Gbps sustained throughput with sub-10ms cross-region latency.
  • Penetration Testing & Vulnerability Scanning: Third-party security auditors executed automated port scans and simulated HTTP attack vectors against public Application Gateway endpoints. 100% of malicious probes were blocked by WAF v2 and Palo Alto NGFW rules.
  • Failover Verification: Simulated an intentional primary firewall instance failure. The Palo Alto Cloud NGFW cluster executed an active-active failover within 3 seconds without dropping active TCP connections.

11. Challenges & Technical Mitigations

Challenge 1: Asymmetric Routing in Multi-Region BGP Paths

Issue: Initial BGP route propagation from Silver Peak SD-WAN appliances caused return traffic from West Europe to route asymmetrically back through East US, triggering Palo Alto TCP stateful drop errors.

Mitigation: Configured BGP AS-Path Prepending and tuned BGP route metrics in Azure Route Server, forcing symmetric inbound and outbound path selection per region.

Challenge 2: Terraform State File Lock During Multi-Hub Deployments

Issue: Parallel Terraform executions across multiple regional hubs created Azure Blob state locking conflicts.

Mitigation: Decoupled the monolithic Terraform codebase into separate regional workspaces (`tf-vwam-core`, `tf-vhub-eastus`, `tf-vhub-westeurope`) managed via GitHub Actions matrix workflows.

12. Lessons Learned & Best Practices

  • Decouple Infrastructure State Files: Structuring Terraform code into independent, modular layers prevents state file corruption and reduces blast radius during network updates.
  • Automate Policy Checks Pre-Commit: Integrating Checkov and OPA Rego policies into GitHub Actions prevents engineers from committing non-compliant `0.0.0.0/0` NSG rules before code reaches production.
  • Leverage Native Cloud NVA Integrations: Deployed Palo Alto Cloud NGFW natively inside Azure Virtual Hub rather than manual VM-Series scale sets reduced maintenance overhead by over 70%.
